# 02. Предпроизводство: GDD, прототипы и вертикальный срез

**Первая редакция:** 2026-10-08 · **Статус:** практический базовый конспект, углубление ожидается.

## Что создаётся до большой разработки

| Документ/артефакт | Зачем | Не включать |
|---|---|---|
| One-pager | Цель, аудитория, жанр, главная механика, отличие | Многотомное описание мира |
| GDD (Game Design Document) | Правила игры, цикл, системы, уровни, UX, баланс | Выдуманные результаты тестирования |
| TDD (Technical Design Document) | Версия Unity, платформа, код/архитектура, данные, зависимости | Непроверенные «100% compatible» |
| Asset inventory | Список требуемых моделей/спрайтов/звуков с лицензиями | Случайные покупки «на будущее» |
| Risk register | Опасности, вероятность/влияние, меры снижения | Игнорирование нетехнических рисков |
| Backlog | Задачи с критериями приёмки и приоритетом | Бесконечный несортированный wishlist |
| Prototype | Быстро проверяет одну механику | Требование финальной графики |
| Vertical slice | Репрезентативный кусок готовой игры с UX/звуком/контентом | Подмена демо огромным проектом |

## Пошаговый план

1. Зафиксировать концепцию и единственный первичный рынок/устройство.
2. Составить GDD с главным циклом, обучением игрока, условием победы, поражением, рестартом.
3. Выписать 3–5 ключевых рисков (число — стартовая рекомендация): управление, FPS, создание ассетов, сохранения, лицензии.
4. Создать дешёвые отдельные прототипы для каждого самого рискованного положения.
5. Провести playtests с наблюдением: что игрок делает без объяснений, где застревает, куда нажимает.
6. Выбрать один фундаментальный сценарий, построить вертикальный срез с близким к релизу качеством (визуал, интерфейс, звук, управление, обратная связь).
7. Оценить реальную скорость производства по вертикальному срезу (например, рабочие часы на тип уровня).
8. Обновить GDD/TDD по фактам и составить production-backlog.
9. Установить контрольные точки: gameplay lock → content complete → alpha → beta → release candidate → релиз. Названия адаптируются к размеру команды.

## Мини-шаблон GDD
```markdown
# Название игры — GDD (ревизия, дата)
## Питч и аудитория
## Целевая платформа, устройства и управление
## Core loop и прогрессия
## Победа, поражение, рестарт
## Механики, противники/цели, ресурсы
## Уровни и кривые сложности
## UI/UX, обучение и accessibility
## Визуальный стиль и аудио
## Сохранения и настройки
## Ограничения, исключённые функции и риски
## Тест-план, метрики и критерии готовности
## Ссылки на прототипы и результаты playtest
```

## Мини-шаблон задачи в backlog
```markdown
### [P1] Реализовать бросок стрелы
**Зачем:** главная механика.
**Вход:** движение/касание для наведения, нажатие/отпускание.
**Выход:** снаряд движется по предсказуемой траектории, столкновение с пугалом, результат.
**Acceptance criteria:**
- Работает на основной платформе.
- Действие повторяемо после Restart.
- Снаряд не поражает человека/другие нецелевые объекты (для учебного демо).
- Нет ошибок в Console во время 10 последовательных пробных запусков.
**Тест:** создать сцену, три дистанции, записать результаты.
```

## Риски и смета
Завести таблицу: `Риск | Вероятность | Ущерб | Ранний сигнал | Ответственный | Контрмера | Дата проверки`. Расходы делить на инструмент, контент, тестовые устройства, публикацию, платные сервисы и резерв. При нулевом бюджете отдельно учитывать затраты времени и зависимости от сервисов.

## Что означает «готово к производству»
- Можно объяснить уникальность игры в двух предложениях.
- Базовый игровой цикл интересен в прототипе.
- Есть воспроизводимая сборка вертикального среза.
- Зафиксирована версия Unity и целевая платформа.
- Известны лицензии критичных ассетов и пакетов.
- Основные технические риски проверены экспериментом или явно ограничены.
- Backlog расставлен по приоритетам с критериями приёмки.
