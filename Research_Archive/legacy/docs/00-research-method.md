# 00. Методика глубокого исследования Unity

**Начато:** 2026-10-08 · **Статус:** стартовое руководство, углубление запланировано · **Основная задача:** [#1](https://github.com/spels1992/Unity/issues/1).

## Цель
Создать практически применимую базу знаний, по которой можно воспроизвести весь процесс: придумать небольшую игру, выбрать инструменты, запрограммировать, протестировать, оптимизировать, выпустить и поддерживать её.

## Карта дисциплин
1. **Продукт/дизайн:** жанр, аудитория, конкурентные аналоги, core loop, UX, сложность, fun, прогресс.
2. **Организация производства:** GDD/TDD, scope, backlog, milestone, budget, vertical slice, управление рисками.
3. **Инженерия:** Unity и C#, данные, сценография, архитектура, версии, автоматизация, UI/Input, физика, навигация, сеть.
4. **Контент:** рисунки/модели/текстуры/анимация/звуки/музыка, права и пайплайн Blender.
5. **Качество:** QA, целевые платформы, частота кадров, память, тесты игроков, доступность, локализация.
6. **Коммерческий цикл:** выпуск, сертификация, маркетинг, аналитика, ценообразование, патчи и live operations.

## Иерархия достоверности
- **A — официальный первоисточник:** Unity Docs/Manual/Scripting API/Package Manual, Unity Hub, release notes, terms, исходный GitHub/лицензия библиотеки.
- **B — воспроизводимый инженерный опыт:** открытые образцы проектов, tests, benchmark, issue с конкретной версией, авторский код и эксперименты.
- **C — вторичные материалы:** сообщества, блоги, форумы, видео. Полезны как практические свидетельства, но не подтверждают версии и безопасность.
- **D — гипотеза:** требуются проверка в Editor и/или дополнительные сведения.

Не использовать маркетинговые «лучший», «100% совместимо» без критериев. **Дата доступа не равна дате публикации**. Привязывать API/пакет к конкретной редакции Unity и целевой платформе. Документы Unity версионируются: `6000.3` и `6000.6` могут описывать разные ветки.

## Шаблон каждой главы
- Короткий ответ: зачем и кому;
- минимальные вводные и определения;
- версия Unity и условия;
- пошаговое воспроизведение;
- минимальный код / настройки;
- сравнение альтернатив с компромиссами;
- ошибки, edge cases, производительность;
- лицензии, платное/бесплатное и риски;
- практический тест и наблюдаемый результат;
- прямые первоисточники и дата последней проверки;
- открытые вопросы и план следующих проверок.

## Матрица для каждого инструмента/библиотеки
| Критерий | Что фиксировать |
|---|---|
| Назначение | Зачем нужен и какую проблему решает |
| Совместимость | Unity Editor, C#, рендер-пайплайн, платформа, другой пакет |
| Лицензия | URL/LICENSE, запрет перераспространения, атрибуция |
| Цена | Бесплатен ли сам пакет, ограничения бесплатного плана/сервиса |
| Зрелость | Последний релиз, changelog, open issues, release cycle |
| Стоимость внедрения | Конфликты пакетов, сложность настройки и обучения |
| Производительность | Накладные расходы, профилирование на реальном устройстве |
| Риски | vendor lock-in, abandonware, security, лицензия, update |
| Решение | Принять / тестировать / отложить / не использовать + почему |

## Порядок и контроль качества
1. Следовать `ROADMAP.md` (27 тем); искать сначала свежие официальные материалы.
2. Делить огромную тему на подисследования, не «закрывать» её после единственного источника.
3. Сохранять каждый результат в GitHub **до** перехода к новому блоку. Номер задачи и URL источника сохранять вместе с анализом.
4. Проверять GitHub чтением файла после коммита и отмечать, что осталось непротестированным.
5. Новые знания вносить дополнением, исправляя ошибки и отмечая изменение даты.
6. Доказательство насыщения: покрыта матрица вопросов + появились минимум несколько разных классов источников + новые поисковые запросы не добавляют важной информации. Это оценивается по теме, а не по всему интернету.

## Текущие ограничения
- Здесь хранится исследование. Не создаётся автоматически работающий Unity Editor или билд на ПК.
- Инструкции «проверить в редакторе» не равны факту тестирования. **Live-тест пока не проведён**.
- Содержание отдельных разделов на первом проходе — основа для дальнейшего углубления, не отметка о полной готовности.
